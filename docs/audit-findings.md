# Verified audit findings

### 1. [high] src/components/checkout/checkout-form.tsx:311
Applied discount survives edits to the code field, so the quoted total is not the amount charged
WHY: The order summary and the pay button read from the `discount` state set by the Apply button (line 114 `const discountCents = discount?.cents ?? 0;`, line 119 `const totalCents = subtotalCents - discountCents + shippingCents;`, line 363 `<Submit totalCents={totalCents} />`), but the value actually submitted is the live input, since the Input carries `name="discountCode"` (line 309) and `value={discountInput}` (line 310). Editing or clearing the field after a successful Apply never clears `discount`. Concrete failure: customer types SAVE10, clicks Apply, summary shows Discount -R45 and the button reads "Pay R555 with PayFast"; they then clear the field (changed their mind, or retyping a different code) and submit. The server sees an empty discountCode, skips `checkDiscount` (checkout.ts line 179 `if (input.discountCode) {`), and creates the order at R600. `PayfastRedirect` auto-submits on mount (lines 65 to 67 `React.useEffect(() => { formRef.current?.submit(); }, []);`), so the buyer is thrown to PayFast and charged R600 without ever seeing the real total. Nothing in the flow reconciles the client quote against the server total, so the same silent divergence happens whenever a price changes after the item was cached into localStorage.
FIX: Clear the preview on any edit: `onChange={(e) => { setDiscountInput(e.target.value); setDiscount(null); }}`. Then close the class of bug properly by having the form post the quoted total in a hidden field and having `createCheckout` compare it to its own `totalCents`, returning a "prices changed, review your order" result instead of a redirect when they differ.

### 2. [high] src/lib/commerce/discounts.ts:39
Discount usage caps are unenforceable: the cap is read at order creation but only incremented after payment settles
WHY: `usedCount` is only ever bumped in the ITN handler, after payment lands (src/app/api/payfast/notify/route.ts line 111 `await redeemDiscount(payload, updated.discountCode);`), and that handler never re-validates the code against its cap before honouring the discount baked into the order. The window between order creation and payment settlement is entirely buyer-controlled. Concrete failure: a code with maxUses 1 and 50 percent off is posted publicly. Ten buyers check out within the same minute; every one of them passes the `usedCount >= maxUses` gate because `usedCount` is still 0, every order is created at half price, and all ten pay. One person can do the same alone by opening several checkout tabs, submitting each, then paying them all. The cap says 1 and the shop honours 10. The `incrementDiscountUse` SQL is atomic, but atomicity on the increment does not help when the check happens minutes earlier on a different read.
FIX: Claim the use at order creation, not at payment: run a conditional atomic UPDATE (`UPDATE discount_codes SET used_count = used_count + 1 WHERE id = ? AND (max_uses IS NULL OR used_count < max_uses)`) inside `createCheckout` and fail the checkout if zero rows changed, then release the claim when an order is cancelled or its payment fails. At minimum, re-run `checkDiscount` in the ITN handler before marking paid and flag the order when the code is no longer valid.

### 3. [high] src/app/(frontend)/account/page.tsx:63
Anyone can read a stranger's order history by registering an account with their email address
WHY: The customers collection is an unverified auth collection that anyone may create through the public REST API, and the account page then bypasses collection access (`overrideAccess: true`) and treats a matching email string as proof of ownership. An attacker registers at /account with victim@example.com, logs in straight away, and is shown every guest order ever placed with that address: order number, date, line items and quantities, status and total, alongside the address as the page header. Guest checkout is first-class here, so most real orders sit in exactly that unlinked, email-only state. It also compounds: `update: staffOrSelfCustomer` (Customers.ts:24) lets a signed-in customer PATCH their own record's email over REST, so one account can be walked from address to address. For an alcohol retailer under POPIA this is customer purchase history disclosed to an unauthenticated stranger.
FIX: Stop treating an unverified email as proof of ownership. Either set `verify: true` on the customers collection so the address must be confirmed before the email branch of the query is trusted, or drop the `email` branch entirely and claim guest orders through a proven step (order number plus a token mailed with the order confirmation). The `{ customer: { equals: customer.id } }` branch is the only one safe to run unverified.

### 4. [high] .gitignore:29
The SQLite database, including staff password hashes, is committed to the git repository and pushed to GitHub
WHY: The whole datastore is under version control and pushed to a remote. As committed it already carries a staff account's password hash and salt from the users table. The exposure grows on its own: the file is tracked, so the next routine `git add -A` from a tree that has served real traffic commits the orders table (name, email, phone, delivery address, date of birth), plus enquiries and subscribers, to GitHub and to every clone and every fork of the history. The .cpanel.yml exclude protects the live database from being overwritten on deploy, but it does nothing about what is already in the repository.
FIX: Add `verboten.db` and `verboten.db-*` to .gitignore, run `git rm --cached verboten.db`, and rotate the credentials of any staff account whose hash is in the history. If the GitHub repository is public, or was ever public or shared, purge the blob from history rather than only removing it going forward.

### 5. [high] src/components/home/hero-cinema.tsx:91
Hero carousel auto-advances every 7 seconds with no pause, stop or hide control (WCAG 2.2.2, Level A)
WHY: The rotating region carries real information: the page's only `<h1>` (line 133, `const Heading = i === 0 ? "h1" : "h2";`), the body copy and the primary CTAs. It changes automatically, lasts far longer than 5 seconds, and runs in parallel with other content, so 2.2.2 requires a mechanism to pause, stop or hide it. There is none. Hover-pause is unavailable to touch users and to anyone reading with a magnifier or keyboard who is not focused inside the hero; focus-pause only helps once you have tabbed in. Worse, tapping a chapter numeral does not reset the timer, so a user who selects chapter III can be thrown to chapter I a fraction of a second later, mid-sentence. Cognitive-disability and low-vision users cannot finish reading a chapter. It also means the page's `<h1>` is inside an `aria-hidden` container for two thirds of the cycle.
FIX: Add a real pause control. Track a user-initiated `stopped` state, add a visible Pause/Play toggle button beside the chapter numerals (labelled, min 24x24 CSS px), and include `stopped` in the `if (paused || reduced || stopped) return;` guard. Also set `stopped` (or at minimum reset the interval) inside the chapter button's `onClick`, so choosing a chapter does not immediately get overridden. Keep the existing reduced-motion behaviour as it is.

### 6. [high] src/components/checkout/checkout-form.tsx:251
Checkout address errors are not programmatically associated with their fields; province never gets aria-invalid
WHY: This is the checkout, the only page that takes money. A screen-reader user who submits with a bad street address, city or province hears the field name and nothing else: the reason for the rejection sits in a `<p>` that is visually adjacent but has no programmatic relationship to the input (WCAG 1.3.1 Info and Relationships, and 3.3.1 Error Identification is only met visually). Province is worse than the other two: because it never receives `aria-invalid="true"`, the recovery routine at line 95, `formRef.current?.querySelector<HTMLElement>('[aria-invalid="true"]')`, finds nothing when province is the sole error, so focus is never moved and the user is left on a form that appears to have silently done nothing. The inconsistency also makes this a straightforward regression rather than a design choice: eight sibling fields in the same file do it correctly.
FIX: Add `aria-describedby={errors?.line1 ? "co-line1-error" : undefined}` to the line1 Input and the equivalent to the city Input. Give the province `<select>` both `aria-invalid={errors?.province ? true : undefined}` and `aria-describedby={errors?.province ? "co-province-error" : undefined}`. Better still, move the wiring into the `Field` component itself (clone the child and inject both attributes from `error`) so no future field can be added without it.

### 7. [high] src/seed/content.ts:20
Banned lockdown reference survived the rebuild into the seeded Story page copy
WHY: Lockdown references are explicitly banned. This is not an accidental echo: the project's own recon dossier at docs/old-site-recon.md:146 identified this exact phrase as the defect to remove, writing '**Dated COVID framing.** The about page hangs the origin story on 2020 lockdown: blending "behind closed doors in Pretoria" "while the world was following orders". Six years on this reads stale and mildly political, and it will age worse.' The rebuild copied the phrase verbatim instead of replacing it. The same file's header comment at line 5 asserts 'Voice rules apply in full: no banned vocabulary', so the file contradicts its own stated contract. The trailing clause 'creativity that only thrives in secrecy' compounds it by implying the spirit was produced illicitly, which is the exact bootleg suspicion the old site's 'Legally produced' line was defensively pre-empting (recon line 142). This is seeded into the CMS as the live Story page body, so shoppers read it.
FIX: Rewrite the sentence to date the founding without the lockdown frame and without the secrecy implication, e.g. 'Verboten started in Pretoria in 2020, built on technical precision and a refusal to accept that a brandy has to taste the way brandy has always tasted.' Then re-seed or edit the Story page in the admin, since the seed only writes pages that do not already exist.

### 9. [high] src/app/(frontend)/template.tsx:12
Every page is server-rendered at opacity:0 by the route template, so nothing paints until the motion bundle hydrates
WHY: The shipped HTML for every route contains `<div style="opacity:0">` around the whole page body. Header and Footer live in layout.tsx and paint, but the actual content (including the LCP hero image and h1 on the home page) is invisible until Next downloads, parses and hydrates the motion client chunk. That converts a fast static paint into a JS-blocked one on every URL, worst on the 3G/mid-range Android traffic this SA store actually gets, and content stays permanently invisible if the bundle fails. It also produces a hydration mismatch for reduced-motion users: server renders motion.div, client returns the bare fragment.
FIX: Drop framer-motion here. globals.css already defines `--animate-fade-in: fade-in 0.9s ease-out both;` and honours prefers-reduced-motion globally at the `@media (prefers-reduced-motion: reduce)` block, so `return <div className="animate-fade-in">{children}</div>` (or deleting template.tsx entirely) gives the same route-change fade with zero JS and HTML that paints immediately. If motion must stay, set `initial={false}` so no opacity is written server-side.

### 10. [high] src/components/motion/reveal.tsx:24
Six home-page sections ship with inline opacity:0 and translateY, and the component's own comment states the opposite
WHY: The comment asserts an invariant the library does not provide. In reality everything below the hero on the highest-traffic page is delivered as `opacity:0; transform:translateY(16px)` and only becomes visible after the motion chunk hydrates and IntersectionObserver fires. Product price, stock badge and the two shop CTAs are inside those blocks, so a slow or failed bundle means a blank scroll and no route to purchase. It also stacks on top of the template.tsx opacity:0 (double JS gate) and adds a second reduced-motion hydration mismatch.
FIX: Either mirror the gallery.tsx guard (`initial={reduce ? false : { opacity: 0, y: 16 }}`), or replace Reveal with the CSS tokens already in globals.css (`--animate-fade-up`, `--animate-rise`) driven by a class, which the global prefers-reduced-motion kill switch already neutralises. Correct the doc comment either way, since it currently documents behaviour the code does not have.

### 11. [high] src/seed/content.ts:243
Batch-numbered journal URL is live, in the sitemap and in JSON-LD

### 12. [medium] src/app/actions/checkout.ts:166
No stock is reserved between order creation and payment, and the decrement floors at zero so the oversell is invisible
WHY: This is the only stock check in the buying path, and it runs at order creation. Stock does not move until the ITN arrives (src/app/api/payfast/notify/route.ts line 109 `await decrementStockForOrder(payload, updated);`), which is minutes later on Instant EFT. Nothing reserves the units in between, and the ITN handler never re-checks availability before flipping the order to paid. Concrete failure: a batch has 1 bottle left. Two buyers both pass `findStockProblems` seconds apart, both are redirected, both pay. The handler marks both paid and takes both payments. The decrement then hides the damage, because src/lib/commerce/atomic.ts line 73 uses `sql\`MAX(0, bottles_remaining - ${units})\`` and clamps at zero instead of failing, so `bottles_remaining` reads 0 and the second sale leaves no trace. Staff discover it only when they cannot pack the second order, and have to refund a customer who was told the order was confirmed.
FIX: Either reserve stock at order creation (a conditional atomic decrement that fails the checkout when it cannot take the units, released when the payment fails or the order is cancelled), or re-check availability inside the ITN handler before the atomic claim to paid, and route an order that cannot be filled to a flagged status with a note for manual refund rather than to paid.

### 13. [medium] src/collections/Orders.ts:224
Orders marked staff-only (internalNotes, payment.raw) are returned to the customer over the REST API
WHY: `admin.description` is a label, not an access rule. A signed-in customer whose order carries the customer relation (set at checkout.ts:203) can GET /api/orders with their session cookie and receive the complete documents, including the two fields intended for staff eyes only. internalNotes is exactly where the webhook writes reconciliation language the buyer should never see, e.g. api/payfast/notify/route.ts:62 `PAYMENT RECEIVED on a ${order.status} order (PayFast ref ...). Reconcile manually.` and route.ts:81 `AMOUNT MISMATCH on ITN: ...`. payment.raw is the stored ITN payload, which includes PayFast's `signature` MD5 over the notification body; since that digest is md5(body + "&passphrase=" + passphrase) and the body fields are handed over in the same object, it is offline guessing material for the merchant passphrase.
FIX: Add field-level read access to both: `access: { read: isAdminOrEditor }` on internalNotes, and the same on the `payment` group (or at minimum on `payment.raw`, keeping `reference` visible if the buyer needs it). Field access is the only thing that filters these out of REST responses.

### 14. [medium] src/components/shop/gallery.tsx:58
Product gallery thumbnails download the 1280px feature file each, because sizes is inert under images.unoptimized

Better still, use the existing CmsImage (or a plain img with mediaSrcSet) for both slots rather than next/image, since next/image is a no-op wrapper under `unoptimized: true`.

### 15. [medium] src/lib/data.ts:226
Bundle offers put the full-resolution original photograph into the cart's 64px thumbnail slot

### 16. [medium] src/lib/seo.ts:102
Event JSON-LD omits the required location.address
WHY: Google's Event structured data spec makes location.address a required property for events with a physical location. Here the Place carries only a name, so every event rendered on /find-us (src/app/(frontend)/find-us/page.tsx:67 maps eventLd over getUpcomingEvents) emits an Event that fails validation and is ineligible for the Event rich result and the Google events experience. The cause is upstream in the data model: src/collections/Events.ts:34 defines location as a single free-text field ({ name: "location", type: "text", required: true }) and the collection has no address, locality or postal-code field at all, so there is nothing for the emitter to read. The same emitter also drops the collection's image field (Events.ts:37-41), another Event property Google recommends. For a brandy house whose discovery depends on markets and tastings, this forfeits the whole events surface in search.
FIX: Add structured address fields to src/collections/Events.ts (streetAddress, addressLocality, addressRegion, postalCode, addressCountry), then have eventLd build location as { "@type": "Place", name, address: { "@type": "PostalAddress", ... } }. While there, pass the event image through and add eventAttendanceMode: "https://schema.org/OfflineEventAttendanceMode".
